# ADR-0005: The GitHub adapter talks over plain `fetch`, with conditional requests

**Date:** 2026-07-25
**Status:** accepted
**Spec:** §2, §6.1, §9
**Issue:** [#11](https://github.com/shaes-farm/dcc/issues/11)

## Context

§6.1 says the GitHub implementation is "REST + GraphQL v4" and stops there. §9's
tech-stack table names a library for every other integration — `@kubernetes/client-node`,
`graphql` + CodeMirror for the playground, `recharts`, `chokidar` — and has no row for an
HTTP client, for GitHub or for anything else. So the first `GitProvider` has to pick one,
and the pick is not obviously an implementation detail: §2 assigns the BFF layer "a single
choke point for the audit log and rate limiting" without saying what rate limiting means
here, and §6.1's acceptance criteria depend on caching that is described only as "warm":

> With `gh` authenticated and 5 repos configured, the repo grid fully renders in **< 3s on
> warm cache**. Alert counts match GitHub UI **within one polling interval**.

§2.1 sets the cadence those criteria run against — Git PRs/checks every 60s, security
alerts every 5m — and §4.1 makes it configurable (`ui.pollingSeconds.git`). Five repos on a
60s poll, each needing a repo rollup, a PR list, an Actions run list and three alert
endpoints, is a standing ~25 requests/minute against a 5,000/hour quota before anyone opens
a second panel. Nothing in the spec says what to do about that.

The obvious default is `@octokit/rest`, which brings pagination, throttling and retry
plugins and endpoint types generated from GitHub's OpenAPI description. Choosing it, or
choosing not to, is the kind of decision the frozen spec left open rather than an ordinary
implementation choice — hence this record.

## Decision

The GitHub adapter uses **Node's built-in `fetch`** through a small internal
`GitHubClient` (`lib/providers/git/github/client.ts`). No `@octokit/*` dependency, no
`graphql` package.

The client owns four things:

- **Auth.** A bearer header from the token `auth.ts` resolved (§6.1's `gh auth token` →
  `tokenEnv` order). The token is constructor state, never logged and never attached to a
  thrown error.
- **Conditional requests.** An in-memory ETag cache keyed by method + URL, sending
  `If-None-Match` and serving the cached body on `304`. This is load-bearing, not an
  optimization: a GitHub `304` does not count against the REST quota, which is what makes
  §6.1's warm-cache criterion and §2.1's 60s cadence affordable together.
- **Pagination.** `Link` `rel="next"` following, with a page cap.
- **Rate-limit accounting.** `x-ratelimit-{limit,remaining,reset}` recorded per response;
  `Retry-After` honored once on a secondary limit. This is §2's choke point, made concrete.

Transport split: **GraphQL v4 for anything that would be N+1 over REST** — the repo
rollups (default-branch check state, open PR count, alert count in one query aliased across
every configured repo) and the PR list (check rollup, review decision and mergeability come
back with the PR instead of costing three REST calls each). **REST for everything GraphQL
does not serve** — Actions runs, and the Dependabot / code-scanning / secret-scanning alert
endpoints. A GraphQL call is a `POST` of a query string, so it needs no client library.

## Consequences

- The client is a constructor away from testable: it takes a `fetch`, so the whole adapter
  is exercised against recorded payloads with no mocking library, matching how the repo
  already tests (`FakeGitProvider`, `uri.fixtures.ts`).
- Caching, retry and quota accounting live in one file we own, at the layer §2 says owns
  them, rather than split between an SDK's plugins and our own BFF.
- We hand-write the upstream payload types we actually read. That is a real cost octokit
  would have covered, bounded by the fact that `normalize.ts` is the only file allowed to
  name an upstream field, so the surface is small and already isolated.
- GitHub REST changes are ours to track. `X-GitHub-Api-Version` is pinned in the client so
  a change is a deliberate bump.
- A second git host (GitLab, Azure DevOps) gets a sibling client rather than inheriting
  this one. That is the §2.2 shape anyway: alternate implementations of `GitProvider`, not
  a shared transport.

## Alternatives considered

**`@octokit/rest` + `@octokit/graphql` + the throttling and retry plugins.** The default
choice, and it does more than we wrote by hand. Rejected on three counts: it adds five
packages to a repo that currently ships zero vendor SDKs, its throttling and retry story
partially duplicates the choke point §2 puts in the BFF (leaving two places that decide
what happens when GitHub says 403), and it has no built-in ETag cache — the one piece
§6.1's acceptance criteria actually turn on — so we would write that anyway, on top of the
dependency. If pagination or endpoint typing later proves expensive, adopting octokit is a
change behind `GitHubClient`, not through the adapter.

**Plain `fetch` with no caching, defer conditional requests to a follow-up.** Smaller first
merge. Rejected because it ships the acceptance criteria unmet by construction: "< 3s on
warm cache" has nothing behind the word warm, and a five-repo workspace burns quota on a
60s poll from day one. The cache is ~40 lines and belongs with the client that needs it.

**Route every GitHub call through GraphQL v4.** One transport, fewer round trips. Rejected:
GitHub Actions and all three alert sources are REST-only, so it is not achievable, and
GraphQL's point-based quota is harder to reason about than the REST one when the panel
cadence is what we are budgeting.
