# ADR-0004: The §8 token ladder is the theme; shadcn's variables alias onto it

**Date:** 2026-07-24
**Status:** accepted
**Spec:** §8, §9, §10.1
**Issue:** #15

## Context

§9 picks "Tailwind CSS v4 + shadcn/ui" for styling. §8 asks for something
shadcn does not ship: dark-only, a near-black background that is not pure
`#000`, one accent color, and status colors as the only saturated colors on
screen. `docs/design/` resolves §8 into concrete values — the `--bg-0..3`
ladder, `--text-1..3`, the accent family, the five status colors and their
14% tints — and every mockup and component prompt is written against those
names.

The scaffold shipped shadcn's generated palette instead: a light `:root` in
`oklch`, a `.dark` block, and no `dark` class on `<html>`, so the app booted
white. Two palettes with different names now had to become one, and the frozen
spec does not say how. Three specific collisions forced a decision rather than
a preference:

- shadcn spends `--accent` on hover and focus _surfaces_; the design system
  spends `--accent` on the one saturated cyan. Same name, different jobs.
- `components/ui/button.tsx` reads `var(--secondary)`, `var(--foreground)` and
  `var(--radius-md)` directly inside arbitrary values, so those names must
  exist as real custom properties, not only as Tailwind theme keys.
- §10.1 allows no external requests, but `docs/design/tokens/fonts.css`
  `@import`s `fonts.googleapis.com`, and the kit says so in its own comment:
  "no font files ship with the source. Google Fonts stand-ins."

## Decision

The design tokens are the theme. shadcn's semantic names survive as aliases
onto them, and nothing else defines a color.

1. `app/globals.css` carries the §8 ladder in `:root`, **copied** from
   `docs/design/tokens/*.css`, not `@import`ed. `docs/design/` is a vendored
   export — prettier-ignored, eslint-ignored, replaced wholesale on the next
   re-export — so the app does not build from it. The kit remains the source of
   truth for what the values are; a value changed in one place and not the
   other is a drift bug.
2. Every shadcn variable (`--background`, `--foreground`, `--card`,
   `--secondary`, `--muted`, `--border`, `--ring`, `--destructive`, `--radius`,
   `--sidebar*`, …) is defined as `var(--<token>)`. There is no second palette
   and no literal color outside the ladder.
3. There is **no light theme**: no light `:root`, no `.dark` override block, one
   palette. `<html>` nonetheless keeps `class="dark"` permanently, because
   shadcn's primitives ship real `dark:` utilities whose branches would
   otherwise never apply. The `dark` class marks a fact about v1, not a toggle.
4. shadcn's `--accent` keeps its shadcn meaning — bound in `@theme` to the
   cyan's dim tint, which is the selection surface the design system already
   uses for active rows. The saturated cyan is reachable as
   `text-accent-strong` / `bg-accent-strong`. Neither name changes meaning
   depending on where it is read.
5. Fonts are self-hosted from `@fontsource-variable/*` (IBM Plex Sans,
   JetBrains Mono), imported in `app/globals.css`. `tokens/fonts.css` is the
   one token file deliberately not adopted.

## Consequences

- One palette, in one file, and a value that appears nowhere in
  `docs/design/tokens/` is a bug on sight.
- The existing shadcn components — `Button`, `ContextMenu`, and the config
  repair screen and unresolvable-URI views built on their tokens — pick up the
  dark theme without being touched.
- The type scale is re-pointed app-wide: `text-base` is 13px, not 16px, and
  `text-sm` is 12px. shadcn primitives inherit DCC's density whether or not
  they were designed for it, which is intended and occasionally means a
  primitive needs its size overridden at the call site.
- `--accent` reading as the dim tint rather than the cyan is a real trap for
  anyone who knows the design system but not this file. It is commented at the
  definition, and `accent-strong` is the escape hatch.
- Re-exporting `docs/design/` will not update `app/globals.css`. Nothing
  enforces that; it is a review obligation, and the copied block says so.
- A light theme, if v2 ever wants one, means reintroducing the `.dark` split
  that this removes. §8 says dark-only for v1 and that is the bet.

## Alternatives considered

**`@import` the token files from `docs/design/tokens/` directly.** No drift
possible, which is the one real advantage. Rejected because it makes a vendored
export a build input: a re-export could change the app's rendering without a
single line of app source changing, and the kit's own `fonts.css` would drag in
a Google Fonts request that §10.1 forbids.

**Keep shadcn's palette and add the DCC tokens beside it.** Two vocabularies
for one screen, and every component author choosing between `bg-card` and
`bg-panel` with nothing to say which is right. This is exactly the widening the
codebase is organized to prevent.

**Rename the design system's `--accent` to avoid the collision.** Would make
`docs/design/`'s prompts and mockups disagree with the code on the name of the
most-used color in the system.

**`next/font/local` with vendored `woff2` files.** Gets Next's preloading and
size-adjusted fallback metrics. Rejected for ~6 binary files in git and
hand-managed versions; `@fontsource-variable/*` is self-hosted either way, and
`unicode-range` means the browser fetches latin only.

**Keep the fonts as Google Fonts stand-ins, as the kit ships them.** Directly
violates §10.1's "no external calls except configured upstreams", and would put
a network dependency in the boot path of a tool whose whole premise is running
locally.
