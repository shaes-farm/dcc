# ADR-0006: `alert://` ids are repo-qualified

**Date:** 2026-07-25
**Status:** accepted
**Spec:** §3.2, §6.1
**Issue:** [#11](https://github.com/shaes-farm/dcc/issues/11)

## Context

§3.2 gives `SecurityAlert` the URI `alert://<provider>/<source>/<id>`, with the worked
example `alert://github/codeql/1234`. The id segment is unqualified, which reads as a
globally unique identifier for the finding.

GitHub has no such identifier. All three sources §6.1 requires the security rollup to merge
number their alerts **per repository**:

- `GET /repos/{owner}/{repo}/dependabot/alerts` → `number` (1, 2, 3… within that repo)
- `GET /repos/{owner}/{repo}/code-scanning/alerts` → `number`, same
- `GET /repos/{owner}/{repo}/secret-scanning/alerts` → `number`, same

So `alert://github/codeql/1234` names a different finding in every repository in the
workspace. §6.1's panel 4 is explicitly cross-repo — "a unified alert table merging
Dependabot, CodeQL/code-scanning, and secret-scanning **across all repos**" — so the
collision is not hypothetical: the rollup is the first thing that renders two alerts whose
URIs are equal and whose contents are not. Everything downstream inherits it, because §3.2
makes URIs the only thing the Knowledge Graph, favorites, and layout presets store.

This is a gap rather than a contradiction. §3.2 does not say ids are provider-native, and
the neighbouring schemes are already composite where the underlying identity is —
`pr://github/acme/checkout-svc/482` carries owner and repo precisely because a PR number
alone means nothing.

## Decision

The `id` segment of an `alert://` URI is **repo-qualified**: `<owner>/<repo>/<number>`.

```
alert://github/dependabot/acme%2Fcheckout-svc%2F42
alert://github/code-scanning/acme%2Fstorefront%2F7
```

The codec already supports this without change. `SCHEME_CODECS.alert` splits its body into
exactly three segments and runs each through `encodeSegment`, whose `SEGMENT_RESERVED`
escapes `/` (`lib/domain/uri.ts`) — so the qualified id is one segment on the wire and
round-trips through `formatUri` → `parseUri` unchanged.

`URI_SCHEMES` is untouched, `SCHEME_CODECS` is untouched, and no new scheme is added.
`docs/ARCHITECTURE.md` is **not** edited — it stays frozen at v0.4; §3.2's example is read
together with this ADR.

The `source` segment uses the normalized `AlertSource` vocabulary already in
`lib/domain/git.ts` (`dependabot | code-scanning | secret-scanning | external`), not
GitHub's endpoint names — §3.2's example writes `codeql`, but the domain's closed union is
what the UI filters on, and one vocabulary per concept is the §3.1 rule.

## Consequences

- Alert URIs are stable and unique across the workspace, so the security rollup, graph
  edges (§3.3's "alerts ↔ repos ↔ services") and favorites all address one finding.
- An alert URI is no longer round-trippable to a single upstream API path without also
  knowing the source's endpoint, which is fine: the adapter owns that mapping, and the
  parsed id gives it owner, repo and number directly.
- The URI is uglier when written out, because percent-escaping is what keeps it one
  segment. It is displayed through `UriChip` and copied through **Copy link**, so the
  escaping is machinery the reader rarely sees, and the alternative is an ambiguous URI.
- A future GitLab or external-scanner `GitProvider` inherits the convention: qualify the id
  with whatever scope makes the source's own numbering unique.

## Alternatives considered

**Keep the bare `number` from GitHub.** Matches §3.2's example exactly. Rejected: it is
wrong the moment two repositories are configured, which is the normal case and the case
§6.1's rollup is built for. Two different alerts would share a URI, and the graph would
merge them.

**Add a fourth segment: `alert://<provider>/<source>/<owner>/<repo>/<number>`.** Reads
better than percent-escaping. Rejected because it changes the scheme's shape and therefore
`docs/ARCHITECTURE.md` §3.2 itself, rather than filling in what the spec left unsaid — and
`ParsedUri`'s `alert` member would gain fields that only make sense for repo-scoped
sources, leaving the `external` source (a Wiz finding, per §6.1) with nothing to put in
them.

**Hash the alert's identity into an opaque id.** Globally unique and one segment, honestly.
Rejected: an opaque id cannot be read at 2am, cannot be reversed to an API call, and throws
away the owner/repo/number the adapter already has in hand.
